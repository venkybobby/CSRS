# Demo Video — Summary and Context

**CSRSupport MVP1 · Meridian Health Plans · prepared 2026-08-16**

Everything needed to record the demo video with Playwright: what is true about
the system today, what already exists to record, the one thing that does not
exist yet, and the recording design.

Read this before writing `scripts/record_demo_video.py`. The awkward parts are
in "Constraints" and "The gap", and both will cost a day if discovered during
a recording session instead of before one.

Two defects were found and closed this week, both surfaced by the client
steering committee's question *"the model picks the procedure — what if it
picks wrong?"*:

- A tie above the match threshold resolved **silently**. Bare `MRI` returned
  MRI Brain without asking.
- A family name inside a sentence (`"M1001 wants an MRI"`) scored below the
  clarify threshold and fell through to **"no rate on file"** — a false
  statement about the rate sheet.

Both are fixed, and both are gated in `evals/demo_scripts.yaml`. The residual
that cannot be engineered away: a *confident* wrong match. If the caller says
knee and means brain, the system prices the knee, correctly. The mitigation is
that the screen always names the procedure and CPT code it priced.

A third finding, later the same week, is worth knowing before you narrate any
figure: **the seeded rates did not match Meridian's own rate sheet** — eight
drifted, four of their procedures missing, three seeded that Meridian never
negotiated. Corrected, and now diffed against `rate_sheet_2026.xlsx` on every
build. Two consequences for a recording: the MRI Brain quote is **$530**, not
the $520 in any older take, and the honest framing of the guardrail is now
sharper rather than weaker — it proves a figure came from the system's data,
and a separate check proves the data is Meridian's.

**The claim to lead with, and the one that survives a sceptic:** the model can
at worst aim the calculator at the wrong procedure. It can never invent what
the calculator returns.

## 3. The gap, since closed: the clarification fixture

**Resolved — kept because the reasoning still governs what target B is for.**
`previewPanes.json` now has 15 panes, one of them `NEEDS_CLARIFICATION`
(`clarify-ambiguous-mri`), and `docs/screenshots/` has the image. Option 1
below was taken. Option 2 remains the only way to show the *exchange*, which
is still the argument for recording target B rather than settling for A.

The original statement of the gap follows, unchanged.

`previewPanes.json` has 14 panes. **None of them is `NEEDS_CLARIFICATION`.**

That matters more than it sounds, because the ambiguity exchange is the single
best new thing to show — it is the client's own question, answered — and it
cannot be recorded from fixtures today. It is also inherently a **two-turn**
interaction (ask → "which one?" → answer → price), and a static pane cannot
express turn-taking at all.

Two ways to close it, and they are not equivalent:

1. **Add a clarification pane to the fixtures.** Extend
   `scripts/generate_preview_fixtures.py` and the `PreviewPane` component to
   render a `NEEDS_CLARIFICATION` result. Gets a screenshot and a
   deterministic pane, but still shows only the question, not the exchange.
   Do this regardless — `docs/screenshots/` should not have a hole where the
   week's headline fix is.
2. **Record the exchange live** (see §4, target B). The only way to show the
   turn-taking that makes the moment land.

Do not hand-edit `previewPanes.json`. It is generated, and
`tests/unit/test_preview_fixtures.py` fails the build on drift.

## 4. Recording targets — pick B, keep A as the fallback

### A — Fixture preview routes (deterministic)

Point Playwright at a local vite dev server and pan across the preview panes.

- **For it**: no auth, no agent, no database, no quota. Reproducible byte for
  byte. Re-runnable in CI if that is ever wanted.
- **Against it**: nothing is *happening*. No typing, no waiting, no answer
  arriving. It is a slideshow with camera motion, and it cannot show the
  clarification exchange at all.

### B — Live local stack against the deployed dev agent (recommended)

Run the vite dev server and the BFF locally, with the BFF pointed at the
deployed dev Agent Engine. Playwright types real questions into the real query
form and records the real answers arriving.

- **For it**: this is a demo. A question is typed, an answer appears, and the
  ambiguity exchange works as an exchange. It is also the only target that
  shows latency honestly.
- **Against it**: each question consumes Reasoning Engine quota (see
  Constraints), and the agent is nondeterministic — a re-record is not
  identical. Requires `DATABASE_URL` for the dev Supabase instance.

```bash
# BFF, pointed at the deployed dev agent
DATABASE_URL=<from secret csrsupport-agent-engine-dev-db-url> \
AGENT_ENGINE_RESOURCE_NAME=projects/375096314532/locations/us-central1/reasoningEngines/1676070786370109440 \
GOOGLE_CLOUD_PROJECT=csrs-504922 GOOGLE_CLOUD_LOCATION=us-central1 \
    uvicorn app.main:app --app-dir bff --port 8080

# Frontend (proxies /api to the BFF)
npm --prefix frontend run dev
```

Note the BFF verifies an IAP JWT in production; running it locally without one
is the documented dev path, but confirm `bff/app/auth.py`'s local behaviour
before assuming the form will submit.

### C — The deployed app behind IAP

Most faithful, and the most painful: Playwright has to complete a Google OAuth
flow. Not worth it for a recording. Use B.

## 6. Playwright recording design

Follow `scripts/capture_demo_screenshots.py`'s conventions — sync API,
chromium, and the same failure posture: a broken route should fail fast and
loudly rather than silently writing an empty artifact.

```python
with sync_playwright() as p:
    browser = p.chromium.launch()
    context = browser.new_context(
        viewport={"width": 1280, "height": 900},
        record_video_dir=str(OUTPUT_DIR),
        record_video_size={"width": 1280, "height": 900},
    )
    page = context.new_page()
    ...
    context.close()   # the video is only finalized on context close
```

Things that will bite:

- **Video is written on `context.close()`, not `page.close()`.** Close the
  context or the file is truncated or missing.
- **Output is `.webm` with a GUID filename.** Rename after close via
  `page.video.path()`. Convert to mp4 with ffmpeg if the deck needs it.
- **`device_scale_factor` is not honoured for video** the way it is for
  screenshots. Record at the size you want; do not expect a 2x file.
- **There is no audio.** Playwright records the viewport only. Narration is
  laid over afterwards — the script for it is already written, in `SLIDES` in
  `scripts/build_demo_deck.py` (press `S` in the deck).
- **Type, do not fill.** `page.type(selector, text, delay=40)` reads as a
  person typing; `fill()` teleports the text in and looks synthetic.
- **Wait on the result, not on a timer.** `page.wait_for_selector` against the
  result component, then an explicit hold. A fixed sleep will race the agent
  on a slow turn and cut the answer off.
- **Reset between shots.** The clarification exchange depends on session
  state; every *other* shot needs a fresh one, or a pending clarification
  leaks into the next question. This is the same member-boundary rule
  `evals/run_eval.py` follows.

## 7. Constraints

- **Reasoning Engine quota is per-minute, per-region, project-wide.** The eval
  suite, CI's post-deploy gate and a live recording all draw on it. Running a
  recording while a deploy build is in flight will fail one of them — this has
  already happened once, and it failed a CI build. Check
  `gcloud builds list --ongoing --region=us-central1` before recording.
- **Do not record during the CSR walkthrough session** for the same reason.
- **The agent is nondeterministic.** Two takes will differ, and a question may
  need re-asking. That is a recording inconvenience, not a defect — but do not
  re-roll a shot that shows a *behavioural* problem. Report it instead.
- **Screenshots must be regenerated before the deck is rebuilt**, and the deck
  before it is published. `capture_demo_screenshots.py` → `build_demo_deck.py`.

## 8. Open items this video does not resolve

Stated so the recording is not mistaken for completion:

- No CSR has used the deployed interface. The walkthrough closes that.
- The guardrail has not been watched firing in the real UI.
- Only `dev` exists; staging and production do not, and forward audit-log
  partition creation is a prerequisite for staging.
- Reasoning engines accumulate in `csrs-504922`, one per deploy since
  2026-08-09, with nothing reaping them. The count was 23 when this was
  written and has grown with every merge since; it was not re-counted for
  this revision, so treat it as a lower bound rather than a figure.
- The rate-sheet update cadence is owned by Finance from September; it was
  the one item marked blocking production on the client's own requirements.
